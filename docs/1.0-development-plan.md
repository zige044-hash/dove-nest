# 鳩巢 Dove Nest 1.0 開發規劃

> 本文件屬於 `feature/dove-nest-1.0` 開發分支。所有功能先在此分支設計、實作與測試；未經使用者明確同意，不合併至 `main`，不更改正式網站、Firebase 或 Vercel 設定。

## 目標

在保留現有作品、登入、草稿與作者管理功能的前提下，逐步加入：
- 會員公開個人頁、暱稱、頭像與簡介
- 作品封面、小說章節、獨立作品詳情頁
- 按讚、留言、收藏
- 雙方同意才建立的筆友關係
- 討論區、檢舉與管理操作紀錄
- 官方公告、維護中畫面
- 創辦人與一般管理員分級權限

## 不可破壞的原則

1. 現有 `stories` 文件與欄位先保持相容；不做批次刪除或破壞性遷移。
2. 草稿只允許作者本人讀取；公開作品才可供訪客瀏覽。
3. 公開個人資料只包含使用者主動設定的暱稱、頭像、簡介等欄位；不公開電子郵件、登入識別資料、真實姓名、聯絡方式或私人資料。
4. 按讚、留言、收藏、筆友邀請等互動需要登入。筆友關係必須雙方同意；本階段不加入陌生人私訊功能。
5. 個人封鎖與全站禁言／停權分開設計；提供檢舉、申訴與管理操作紀錄。
6. 權限必須由 Firestore／Storage 安全規則或可信任的伺服器端驗證，不能只靠前端隱藏按鈕。
7. 創辦人最高權限不可由一般管理員或一般使用者撤銷；一般管理員不可任命或撤銷管理員。
8. 維護模式啟用後，訪客看到維護畫面；管理通道必須以可信任權限驗證，不可只依賴前端繞過。
9. 封面與頭像上傳需限制檔案類型、大小與存取權限；Storage 尚未完成設定前，不假設上傳功能已可用。
10. 任何正式版部署前，先在預覽環境測試，並確認可以回復上一個穩定版本。

## 建議資料結構（待安全規則核對後定稿）

- `users/{uid}`：僅存公開個人資料與必要的帳號狀態；私密資料不得混入公開可讀文件。
- `stories/{storyId}`：延用既有作品欄位，逐步新增封面與章節相關中繼資料。
- `stories/{storyId}/chapters/{chapterId}`：章節內容、排序、發布狀態與時間。
- `stories/{storyId}/likes/{uid}`：每位會員對同一作品最多一筆按讚紀錄。
- `stories/{storyId}/bookmarks/{uid}`：每位會員對同一作品最多一筆收藏紀錄。
- `stories/{storyId}/comments/{commentId}`：留言與作者、時間、狀態欄位。
- `penPalRequests/{requestId}`、`penPalRelations/{relationId}`：邀請與雙方接受後的關係分開保存。
- `discussions/{topicId}` 與回覆子集合：討論主題及回覆。
- `reports/{reportId}`、`moderationLogs/{logId}`：檢舉與管理操作紀錄。
- `announcements/{announcementId}`、`siteConfig/maintenance`：公告與維護狀態。

以上是概念模型，不代表目前資料庫已建立這些集合。正式採用前必須逐項設計安全規則與索引。

## 開發階段

### 0. 基線與安全準備
- 確認獨立分支與正式版基線。
- 找出目前實際生效的 Firestore 規則、部署設定與既有資料形狀。
- 設計預覽測試與回復流程。

### 1. 會員個人頁
- 建立安全的公開個人資料模型。
- 顯示暱稱、頭像、簡介與公開作品。
- 暱稱／頭像修改僅限本人；公開資料採明確白名單。

### 2. 作品詳情、封面與章節
- 從書架卡片進入獨立作品詳情頁。
- 延用既有作品文件，新增封面與章節資料。
- Storage 設定及規則確認後才啟用圖片上傳。

### 3. 按讚、留言、收藏
- 使用每位會員唯一的互動文件，避免重複按讚／收藏。
- 留言提供檢舉與管理狀態；驗證讀寫權限。

### 4. 筆友與討論區
- 筆友邀請採雙方同意；提供拒絕、取消與封鎖。
- 討論區提供分類、主題、回覆與檢舉。
- 不公開聯絡方式，不預設提供私訊。

### 5. 管理、公告與維護模式
- 實作創辦人／一般管理員權限分層。
- 加入禁言、停權、申訴、檢舉與稽核紀錄。
- 公告與維護狀態採受權限保護的設定。

### 6. 整合測試與發布
- 驗證訪客、一般會員、作者、一般管理員、創辦人各種權限。
- 測試舊作品、草稿、Google 登入與手機版。
- 先部署預覽版；取得明確同意後才安排正式版維護畫面與更新。

## 目前已知待確認事項

- Firestore 規則目前未在此儲存庫找到版本控管檔；需要先取得 Firebase Console 中實際生效的規則，避免覆蓋現有權限。
- Firebase Storage 尚未確認已啟用。
- 管理員角色的可信任建立方式，需先核對 Firebase Spark 方案可用能力，再決定安全實作；不可讓使用者自行修改自己的角色。
- 目前首頁仍是單一頁面元件；後續應逐步拆分功能元件，避免一次性大改。
